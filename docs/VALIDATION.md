# 验证记录

这里汇总 sunsetglow 与实况的对比、参数是怎么定下来的、目前已知的漏报，以及和其他预报工具的比较。
README 里的准确度表格就来自这里。

所有回测都可以用仓库里的 [`backtest.py`](../backtest.py) 复现（上海那组的实况数据属于 sunsetbot，不在仓库里）。

**评价指标**

- **Spearman**：指数和实况等级的秩相关，1 表示排序完全一致，0 表示没有关系。
- **AUC（≥小烧）**：把实况「小烧及以上」当作正例时，指数区分正反例的能力。0.5 等于瞎猜，1 表示完美区分。

实况等级统一用 0–4：0 无、1 微烧、2 小烧、3 中烧、4 大烧，可以用半级（如 2.5 表示小到中烧）。

## 汇总

| 数据集 | 事件数（≥小烧） | Spearman | AUC（≥小烧） | 备注 |
|---|---|---|---|---|
| 上海，sunsetbot 公开实况 | 20（7） | +0.63 | 0.88 | sunsetbot 自己的回算：+0.84 / 0.98 |
| 加州，PhenoCam 摄像头 | 87（7） | +0.44 | 0.86 | 摄像头只朝一个方向、30 分钟一帧 |
| 日本，实地观测 | 2（2） | — | — | 两次都明显低估，见下文 |

以上都是默认设置：`gfs025`、云块 30 km、气溶胶标高 1 km，带地形。

## 上海：sunsetbot 公开实况

**数据**：sunsetbot「准确率」页公开的上海实况等级，2022-06-24 至 07-03 共 20 次日出/日落，13 次不烧、7 次有烧，
每条都附有 sunsetbot 当时的预报，可以作对照。实况数据属于 sunsetbot，所以没有放进本仓库。

| 模型 | Spearman | AUC |
|---|---|---|
| 部分云量均匀铺开（初版） | +0.39 | 0.67 |
| 云块模型，云块 30 km（默认） | +0.63 | 0.88 |
| 云块模型，云块 100 km | +0.76 | 0.97 |
| sunsetbot 自己的预报 | +0.84 | 0.98 |

**结论**

- **初版漏了 3 次大烧。** 45% 的云量均匀铺开后，低角度的阳光走几公里就被挡死了。
  而实际的碎云之间有缝，光能透过去。因此改成云块模型：部分云层看作每 *L* km 一个云块，光线以云量 *c* 的概率遇到云块
  （`CLOUD_ELEMENT_KM`）。
- **云块尺度取 30 km。** 云块越大分数越高，一直到 100 km 都在涨，但 100 km 的云块已经不太符合物理，
  很可能是在补偿 GFS 高估的云量。样本只有 20 个，所以先取保守的 30 km。
- **指数刻度按这组数据定。** 「≥小烧」的最佳切分约 1.1，「≥中烧」约 1.5，地图的分级颜色也跟着调整。

**局限**

- 这段时间 CAMS 气溶胶存档还没开始（约 2022-08 起），AOD 一律用缺省值 0.2。
- sunsetbot 的对照预报是事后用 ERA5 再分析算的，比真实的预报占便宜。
- 只有 10 天、一个城市，远远不够。

## 加州：PhenoCam 摄像头

**数据**：[PhenoCam](https://phenocam.nau.edu) 研究用网络摄像头的公开存档。

- **站点**：两个朝西、天空开阔、黄昏曝光正常的加州湿地站点（hillslough、eastend）。
- **采样**：2022-09 至 2025-08 之间随机抽取日期，每天取日落后 3–35 分钟的帧。
- **评级**：由 AI 模型（Claude）逐张目测评 0–4 级，共 87 次，其中 7 次达到小烧及以上。
- **文件**：标签在 [labels/phenocam_california.csv](../labels/phenocam_california.csv)，取图工具是
  [tools/phenocam_labels.py](../tools/phenocam_labels.py)。
- 这段时间有真实的 CAMS AOD。

| 云块尺度 | Spearman | AUC |
|---|---|---|
| 0（均匀铺开） | +0.26 | 0.67 |
| 10 km | +0.39 | 0.79 |
| **30 km（默认）** | +0.44 | **0.85** |
| 100 km | +0.46 | 0.83 |

（此表是加入地形之前算的；加入地形后，默认设置为 +0.44 / 0.86。）

**结论**

- **云块模型在独立数据上同样有效。** 它明显好于均匀铺开，30 km 基本就是最优，支持在上海选定的取值。
- **默认模式因此改为 `gfs025`。**
  - Open-Meteo 的 `gfs_seamless` 在美国会混入 HRRR，而 HRRR 的分层云量里几乎没有高云，结果 3 次大烧当天指数都是 0；纯 GFS 给出 0.6–1.3。
  - ECMWF（`ecmwf_ifs025`）3 次中漏了 2 次。
  - 在美国以外，`gfs_seamless` 与 `gfs025` 相同。
- **两地的档位对不上。** 加州「≥小烧」的最佳切分约 0.4，上海约 1.1。可能的原因有两类：
  - 评级方式不同：评级人不一样，摄像头也只朝一个方向、30 分钟一帧，容易漏掉短暂的烧云。
  - 两地气候不同。
- **自动按颜色打分不可用。** 晴天的暮光带和真正的云霞分不开，所以改为目测评级，标签难免带评级人的主观性。

## 地形

遮挡看的是「从云的位置看，山有多高」，而不是山本身有多高。合成场景（[`test_synthetic.py`](../test_synthetic.py)）：

| 场景 | 平地 | 有山 |
|---|---|---|
| 1.5 km 低云，80 km 外有 2 km 山脊 | 0.21 | 0.21 |
| 1.5 km 低云，40 km 外有 3 km 山脊 | 0.21 | 0.01 |
| 5.5 km 中云，40 km 外有 3 km 山脊 | 0.56 | 0.54 |
| 9 km 卷云，40 km 外有 3 km 山脊 | 1.16 | 1.14 |

实际数据上：

- **东京**：2026-10-24 至 31 共 16 次日出日落，带地形和平地的指数相差都在 ±0.01 以内。
- **加州**：87 个事件，带地形 Spearman 0.44 / AUC 0.86，平地 0.45 / 0.86，没有一个事件的指数变化超过 0.05。
  这两个站点都在三角洲平原上，西面的海岸山脉不到 1 km 高。

所以在平原城市，地形几乎不改变结果。地形影响大的是山区或山脚下的观测点，
以及在山上往下看云海的情况，这时观测点的海拔会改变视线。

## 日本：实地观测与漏报

标签在 [labels/field_japan.csv](../labels/field_japan.csv)，由维护者现场观测。两次都是明显的低估。

### 奈半利（高知），2026-11-02 日落：实况 3.5，指数 0

日落后，头顶和南侧的高积云整片被染成粉橙色，而 `gfs025` 和 `ecmwf_ifs025` 给出的指数都是 0。

**原因 1：薄层高积云落在两个气压层之间。** 观测点附近 150 km 内，两个模式的分层云量全是空的，
但模式按整层大气诊断的中云量其实看到了这层云：

- ECMWF：中云 54–72%（16 时）→ 25–34%（17 时）。
- GFS（`gfs_global`）：16 时中云 100%，17 时已经退到背日侧 100 km 以外。

于是试了用诊断量把云补回截面里（`--diag`）：

| 做法 | 上海 AUC | 加州 AUC | 奈半利 GFS / ECMWF |
|---|---|---|---|
| 不补（默认） | 0.88 | 0.86 | 0.00 / 0.00 |
| 诊断量高于分层云量就抬高 | 0.77 | 0.76 | 0.01 / 0.35 |
| 只补完全没有云的层段（`--diag`） | 0.88 | 0.84 | 0.01 / 0.35 |

- **把已有云层抬高，结果明显变差。** GFS 的诊断量几乎只有 0 和 100 两个值，抬高已有云层会把太阳一侧的光全部挡死。
- **只补空层段，作用也有限。** 这种做法在旧数据上基本中性，但这次也只把 ECMWF 救到了微烧。所以 `--diag` 默认关闭。

**原因 2：GFS 移云太早。** GFS 把这条云带移走的时间比实际早了大约 1 小时。

**原因 3：云不在截面上。** 被染红的云主要在南侧，不在太阳方位的那条截面上，而 sunsetglow 只计算这一条截面。

原因 2 和 3 都不是补层能解决的。

### 东京，2026-11-10 日落：实况 4，指数 0.50（GFS）/ 0.78（ECMWF）

从高层朝西看（富士山可见），日落后整片高积云从头顶一直铺到西边地平线，被染成深红橙色。
西边地平线上方留有一道晴空缺口，阳光就是从这里照进云底的。

- **对的部分**：两个模式都算出了日落前后 12–20 分钟的发光，色调偏红，峰值就在日落时刻。
- **错的部分**：强度明显低估。按上海的档位，0.5–0.8 只算「微烧」。

加上奈半利，日本这两次中烧以上的实况，指数都在 1.0 以下。日本是否需要更低的档位，要等样本攒够才能下结论。

## 和其他工具对比（东京，2026-10-24 至 31）

参与比较的有：

- **Sunsethue**：0–100%，输入是 ICON。公开网页可以看到近 5 天的历史和未来 3 天的预报。
- **Alpenglow**：只公开第二天的预报。
- **sunsetglow**：GFS 输入，带地形。另外也用 ICON 输入算了一列，用来区分差异来自数据还是算法。

| 日期 | 事件 | sunsetglow | Sunsethue | Alpenglow | sunsetglow 改用 ICON 输入 |
|---|---|---|---|---|---|
| 10-25 | 日落 | 0.36 | 1 | | |
| 10-27 | 日出 / 日落 | 0.28 / 0.34 | 0 / 0 | | |
| 10-28 | 日出 / 日落 | 0.04 / 0.18 | 39 / 39 | | 日落 0.06 |
| 10-29 | 日落 | **1.51** | 4 | | 1.09 |
| 10-30 | 日出 / 日落 | 0.00 / 0.17 | 0 / 1 | 70 / 64 | 日落 1.14 |
| 10-31 | 日出 / 日落 | 0.00 / 0.00 | 34 / 43 | | 0.01 / 0.40 |

其余 6 个事件，三方都接近 0。

- **各家工具之间本身就对不上。** 16 个事件上，sunsetglow 与 Sunsethue 的 Spearman 只有 0.04；
  10-30 日落，Sunsethue 给 1%，Alpenglow 给 64%。
- **差异的来源**：都换成 ICON 输入后，10-31 的差距有一部分来自模式云量（GFS 0 → ICON 0.40），
  而 10-29、10-30 的差距来自算法本身。
- 这一周没有实况记录，判断不了谁对；三家也都没有公开过校准数据。
